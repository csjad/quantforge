# D-002｜数据库选型（数据层在线读写库）

- 状态：已接受｜日期：2026-11-13｜决策人：角色1（A1 裁决），A2 会签
- 来源：工程正文 S01 技术正文表5，项目内闭环（含 C-021 内部冲突消解）

## 背景与约束
- S01 的选型核心问题：**分析型查询与写入并发能否兼得**——本系统存在"回测任务并发读、数据同步并发写"的真实场景。
- 承载范围：在线读写库承载标的元信息、策略注册、回测任务、结果摘要、因子缓存、风控规则、快照登记；K线行情主存为 Parquet 列式分区（见"混合存储三层"）。

## 备选方案与打分（表5，工程正文原文数值；依据句为本轮补充）
| 维度（权重） | 方案甲 SQLite | 方案乙 PostgreSQL | 方案丙 DuckDB |
|---|---|---|---|
| 写入并发（0.25） | 弱，单写锁 | 强，多连接 | 中，适合批量导入 |
| 分析查询（0.30） | 中，需手工索引 | 强，索引与分区成熟 | 极强，列式扫描 |
| 部署成本（0.20） | 无，单文件 | 中，需容器与账号 | 无，嵌入式 |
| 运维难度（0.15） | 极低 | 中 | 低 |
| 生态兼容（0.10） | 高 | 极高 | 中，工具链较新 |
| 加权总分 | 3.4 | **4.2** | 3.9 |

依据句：SQLite 单写锁会在批量导入时阻塞回测读，与"并发读+并发写"场景直接冲突；PostgreSQL 的备份与恢复、分区表、按时间范围查询三项为成熟能力，直接服务 S14 备份体系；DuckDB 的向量化执行与列式扫描适合即席聚合，但工具链较新、不承担在线事务。

## 决策（D-002 选定方案乙 PostgreSQL）
理由两点：
1. 本系统存在"回测任务并发读、数据同步并发写"的真实场景，SQLite 的单写锁会在批量导入时阻塞回测。
2. 备份与恢复、分区表、按时间范围查询在 PostgreSQL 中为成熟能力，直接服务于 S14 备份体系。

## C-021 消解：混合存储三层（K线不走PG行存）
工程正文深度展开表7（五方案比较）结论：**Parquet 存K线，DuckDB 做即席聚合查询，SQLite 存元信息/任务/快照**——与 D-002 存在内部冲突（C-021）。消解定稿（选定方案1，见 S00-07）：

| 层 | 承载 | 职责 |
|---|---|---|
| Parquet 分区文件 | bars_raw、bars_adj | K线行情主存，按 标的+年（日线）/标的+年月（分钟线）分区，列式高压缩，写入吞吐高、按分区追加 |
| PostgreSQL 16 | symbols、strategies、bt_tasks、bt_results、factors、risk_rules、snapshots、隔离表、审计表 | 在线读写：元数据、任务状态、结果摘要、因子缓存、风控规则、快照登记；事务与备份成熟 |
| DuckDB | 进程内即席引擎 | 跨分区聚合、临时核查、离线分析辅助，**不承担在线读写** |

不把 K线塞进PG行存的口径：单机用户没有等待数小时 DDL 的耐心，分钟线单表超一亿行后任何 DDL 都要跑数小时——"省事"的代价是灾难。SQLite 不承担核心职责，仅作离线交付包内的引导轻库（可选）。

## 版本与假设
- 数据库版本锁定 **PostgreSQL 16**；版本不一致时迁移脚本需重测（新增假设，随 S01 冻结）。

## 后果与影响
- S02 拉取逻辑写 Parquet 分区 + PG 元数据登记双通道；S03 引擎读取走 DuckDB 加速 Parquet（列裁剪+谓词下推）；S12 任务状态落 PG（事务保证）；S14 备份对象=PG 库 + Parquet 分区清单（快照式，非复制）。
