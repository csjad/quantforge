## 2. 冲突登记（本阶段）

### C-001｜分钟线标的池约束（工程正文原生，本阶段闭环）
- 发现阶段：工程正文S01 → 项目S01
- 冲突原文甲：S00要求"分钟线只存五百只"
- 冲突原文乙：表结构未限制标的范围，上层无约束可能被写入全市场分钟线
- 量化差值：全市场1min年增约3.17亿根（约30GB/年量级）vs 池内500只年增约1.46亿根（约14.4GB/5年量级），超限数倍
- 风险等级：高
- 失效后果：磁盘配额失守，回测加载超时
- 方案1：入库层标的池白名单校验
- 方案2：数据库层触发器拦截
- 方案对比：路径一错误信息更友好、便于教学演示；路径二拦截点更深但报错对新手不友好
- 选定方案：方案1（入库层白名单校验）
- 需回溯修改的清单：S02拉取逻辑、S19容量说明、本设计文档§6.4（已写入）
- 修改完成确认标记：已完成

### C-021｜工程正文内部：PG与SQLite职责（本阶段闭环）
- 发现阶段：工程正文S01内部（技术正文 vs 深度展开）
- 冲突原文甲：D-002选定PostgreSQL承担在线读写
- 冲突原文乙：深度展开表7结论"SQLite存标的元信息、任务状态、快照登记与回测摘要索引"
- 量化差值：元数据/任务/快照承载库不同（PG vs SQLite）
- 风险等级：中
- 失效后果：双库并行承载同一职责，备份与一致性设计双轨冲突
- 方案1：PG承担全部核心职责，SQLite仅作离线交付包引导轻库（可选）
- 方案2：SQLite承担元数据/任务/快照，PG仅存行情相关
- 方案对比：方案1与D-002正式决策一致、备份只需一套；方案2与决策记录直接矛盾
- 选定方案：方案1（混合三层定稿：Parquet K线主存 + PostgreSQL 在线读写 + DuckDB 即席，SQLite仅交付包引导可选）
- 需回溯修改的清单：本设计文档§2.3、S12任务系统、S14备份设计、S15审计
- 修改完成确认标记：已完成
