## 2. 任务状态机（五状态，状态写数据库非内存）

**五状态**：待排队、运行中、成功、失败、已取消。
**合法迁移**：待排队→运行中；运行中→成功/失败/已取消。**其余迁移一律拒绝并记录**。
**状态写入数据库而非内存**——回测任务可能运行数十分钟，期间重启是常态；若状态只在内存中，重启后会出现**"任务消失但进程仍在跑"的僵尸现象**。

### 2.1 表24 任务状态与允许操作

| 状态 | 允许操作 | 禁止操作 |
|---|---|---|
| 待执行 | 执行、取消 | 查询结果 |
| 运行中 | 取消、查进度 | **改参数（硬拦截）** |
| 成功 | 查结果、重跑 | 取消 |
| 失败 | 重跑、查日志 | 查结果 |
| 已取消 | 重跑 | 查结果 |

**"运行中禁止改参数"必须硬拦截**：允许改参数会让同一任务标识对应两组参数，而结果表以任务标识为键，最终出现"**结果属于哪组参数无法确认**"的死结。

### 2.2 任务状态五个字段
状态、**进度**、最近心跳、累计耗时、失败原因。
- **进度 = 已完成分片数÷总分片数，不用百分比取整**——取整会让长任务长时间显示同一个数字，使用者据此判断"卡住了"；
- **进度显示数值设计**：保留一位小数；**总分片超1000改为"已完成数+总量"**——千级分片上百分比每完成一个只跳0.1个百分点，界面看起来不动；减少"是不是卡住了"的反复询问（长任务最需要耐心时最常问）。

## 3. 取消机制（协作式，不强制杀线程）

**取消请求写入数据库标志位**，工作进程在**每个参数组合开始前检查标志**，发现取消则保存已完成结果并退出。**不采用强制杀线程**——强制终止会中断文件写入，导致结果文件损坏。取消后任务状态=已取消，**已产出部分结果仍可查看，但不计入统计**。

**取消流程四步**：置取消标志 → 通知子进程 → 等待退出 → 回收资源。
- **等待退出上限20秒**，超时强制结束并**登记"强制回收"**；
- **资源回收三样：子进程、临时目录、内存映射文件**，**缺一都会留下占空间但不显示的残留文件**；
- **强制回收必须登记，不可静默**——强制结束可能让子进程在写结果文件的瞬间被杀，留下半写文件；若静默回收，这个半写文件会被下一次同参数任务**误认为已完成结果**。

## 4. 超时与重试

- **单任务超时默认30分钟**，超时后标记失败并**记录最后完成的分片索引**（断点续跑依据）；
- 失败任务允许重试，**重试上限2次**，超限进入人工处理队列；
- **重试不复用原任务参数快照，复制一份新快照**——保证可追溯。

## 5. 归档清理（三级周期，与 S14 备份对齐）

| 任务类型 | 保留期 | 处置 |
|---|---|---|
| 成功任务 | **90天** | 超期移归档表，主表软删除 |
| 失败任务 | 30天 | 同上 |
| 已取消任务 | 7天 | 同上 |

**归档策略须与 S14 备份策略对齐**，避免"备份了又被归档删除"的重复占用。

## 6. 幂等与重入

**所有任务操作必须幂等**：
- 重复提交同参数同快照 → 返回已有任务标识，**不新建**；
- 重复取消已完成任务 → 返回已完成，不报错；
- 重复查询进度 → 结果一致。

**唯一约束 = 参数哈希 + 快照号 + 策略标识三列联合唯一**。
非幂等的典型故障："点两次提交按钮跑出两条任务，两条任务抢同一份缓存目录，**结果互相覆盖**"——这类故障开发期很难遇到，**交付后极常见**，因为买家网络慢会重复点击。

## 7. 一次任务的全生命周期（深入推导）

提交时写入**待执行**并返回任务标识 → 调度器取出置**执行中**，写开始时间与心跳 → 每完成一个分片更新进度 → 全部完成写结束时间、**结果路径与摘要**，置**已完成** → 中途异常退出，重启时把执行中**回退为待执行**。

**关键点："结果路径在完成时才写"**——若在执行中就写路径，重启后的清理逻辑会把半成品当成成品，从而把失败任务算作成功。

## 8. 心跳与假死判定

- **心跳每30秒写一次，超过120秒未更新判定疑似失败并允许人工接管**；
- **心跳写数据库不写日志**——日志在崩溃时可能丢失缓冲，数据库有事务保证；
- **四倍关系不是随意的**：给一次GC停顿、一次磁盘抖动、一次数据库慢查询的余量。阈值取两倍→正常但繁忙的任务被误判假死；取八倍→真死的任务要等四分钟才被发现。
