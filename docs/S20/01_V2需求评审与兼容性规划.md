## 2. 需求增补五条（表35）

| 编号 | 需求 | 优先级 | 兼容等级 |
|---|---|---|---|

**优先级按"影响回测结论正确性"排序**：组合账户与再平衡为必须，ETF为应该，其余为可以做。
**前三条为强需求，后两条为体验需求。**

**优先级判定三问**（每个需求必答）：**为什么V1没做、做了谁获益、不做会怎样**。
- 第二问必须落到具体角色与场景（如"想跑多标的组合的人，同时持有10只股票时要手工算再平衡"）；
- **"不做会怎样"决定优先级**：可以手工绕过→降为"可以"；会产生错误结论→升为"必须"。
- **实例**：多账户并行→手工分两次跑可绕过→降为"可以"；**ETF分红→不做会怎样=分红日收益被算成暴跌，结论完全错误→升为"必须"**。

## 3. 兼容性判断（核心决策：**V1 策略接口不改**）

**V1 的策略接口是否需要改动，是 V2 的核心问题。结论是不改。**
- 单标的策略在组合模式下被**包装为"对每个标的独立运行、共享同一账户"**，**策略代码无需感知组合**；
- **代价**：组合级逻辑（如资金分配）由引擎层负责，策略无法参与；
- **收益**：**V1 策略全部可复用，买家升级不需要重写策略**。

| V1 资产 | V2 状态 | 说明 |
|---|---|---|
| **策略接口** | **完全兼容** | 单标的策略直接可用 |

### 3.2 兼容性承诺三级

| 等级 | 承诺 | 说明 |
|---|---|---|
| **一级 数据兼容** | ✅ 承诺 | V1 快照可直接被 V2 打开，不需重导入 |
| **二级 结果兼容** | ✅ 承诺 | 同一策略同一参数同一快照，V1 与 V2 核心指标偏差**≤千分之五** |
| **三级 行为兼容** | ❌ **明确不承诺** | 信号时点与成交笔数完全一致 |

**不承诺三级的原因**：V2 引入组合调仓，**调仓逻辑会改变部分信号时点，行为必然变化**。**若不声明，老用户升级后看到成交笔数变化会认为程序出错；声明不承诺三级，反而让变化成为预期。**

## 4. 资源增量预估

- **内存**：组合模式同时持有10标的，行情读取量约为单标的10倍，**内存估算从1.5GB上升至4GB**，**须在 S21 验证**；**不达标则限制组合规模为5标的**；
- **磁盘**：组合调仓存每日持仓明细，单任务5000行×100字节=500KB，1000任务约0.5GB；组合持仓表常驻约20MB；**两项合计不到总量2%，符合一成上限**（超一成拆分到V3）；
- **教程**：新增3章约15页，**未超4章上限**，允许同版更新目录（超4章须同步重写目录，防教程结构随迭代崩坏）。

## 5. 冲突 C-035｜资金分配时机（工程正文S20原生 C-008，项目编号顺延）

- 发现阶段：工程正文S20内部 → 项目S20（工程正文内部编号C-008；项目C-008已被端口冲突占用，顺延为C-035）
- 冲突原文甲：V1 账户模型为单账户单标的**串行处理**
- 冲突原文乙：组合模式要求**并行决策**
- 量化差值：资金分配时机不同（逐标的串行 vs 并行统一分配）
- 风险等级：高（组合再平衡时序错误→资金分配错乱，三守恒式失效）
- 失效后果：调仓资金重复占用、部分成交部分失败、资金凭空出现
- 方案1：**引入两阶段决策——先收集全部标的信号，再统一分配资金，最后批量提交委托**
- 方案2：逐标的串行分配（沿用V1模型）
- 方案对比：方案1保证资金统一调度不重复占用；方案2在组合场景下资金分配错乱
- **选定方案：方案1（两阶段决策）**
- 需回溯修改的清单：**S03 时钟推进说明**（九步时序扩展组合模式分支）
- 修改完成确认标记：已完成
